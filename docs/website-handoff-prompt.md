# พรอมป์ต์ส่งต่อให้ AI ที่พัฒนาเว็บไซต์เดิม

คัดลอกข้อความตั้งแต่ “คุณกำลังรับช่วง…” ถึงท้ายเอกสารไปให้ AI ในโปรเจกต์เว็บไซต์เดิม พร้อมแนบ `docs/ai-integration.md`, `docs/openapi.json` และ `integration/ruamwan-client.mjs` จากชุดร่วมวัน 0.10.0 เอกสารนี้ไม่ได้สมมติว่าได้ตรวจโค้ดเว็บไซต์ปลายทางแล้ว ให้ AI อ่านเว็บไซต์จริงก่อนระบุไฟล์ที่จะแก้

---

คุณกำลังรับช่วงเชื่อมเว็บไซต์ของฉันกับร่วมวัน AI API 0.10.0 ฉันพอใจโครงสร้างเว็บไซต์เดิมแล้ว ให้ลงมือเชื่อมฟังก์ชันและข้อมูลเข้ากับหน้าเดิม ห้ามรื้อหน้า เปลี่ยน navigation ออกแบบ layout ใหม่ เปลี่ยน framework หรือสร้างเว็บไซต์แทนของเดิม ถ้าขาดช่องหรือสถานะที่จำเป็น เพิ่มเฉพาะส่วนเล็กที่สุดให้เข้ากับ design system เดิม เน้นใช้ง่าย ตัวอักษรอ่านง่าย ปุ่มชัดเจน ใช้ได้ทั้งผู้สูงอายุและคนทั่วไป ไม่บังคับกรอกข้อมูลสุขภาพครบเพื่อเริ่มบันทึก

## สิ่งที่ต้องอ่านและส่งมอบ

1. ตรวจ framework, routes, components, state management, backend, login, ฐานข้อมูล และรูปแบบ UI ที่มีจริงก่อนแก้ อ่านคำสั่งใน repo และเอกสาร API ที่แนบ
2. ทำตารางจับคู่ “ความสามารถร่วมวัน → หน้า/component เดิม → endpoint → ข้อมูลที่อ่าน/เขียน → ไฟล์ที่ต้องแก้” ใช้ชื่อไฟล์จริงจาก repo อย่าเดาชื่อไฟล์ หากมีฟังก์ชันเดิมอยู่แล้วให้ต่อยอด
3. ลงมือเชื่อม backend และ frontend ให้ครบ ทดสอบ flow จริงกับ API และสรุปไฟล์ที่เปลี่ยน วิธีรัน และข้อจำกัด หากติดตั้ง API บน host ปลายทางไม่ได้ ให้แยกสถานะเชื่อมไม่ได้อย่างตรงไปตรงมา ไม่ใช้ข้อมูล mock เป็นหลักฐานว่าต่อโมเดลได้แล้ว

## AI นี้ทำงานอย่างไร

ร่วมวันเป็นบริการ Python/FastAPI บน Mac Apple Silicon ใช้ Typhoon2.5-Qwen3-4B แบบ MLX 4-bit พร้อม LoRA ที่เลือกใช้เฉพาะ intent/menu โมเดลไม่ได้ทำทุกอย่างเอง โปรแกรมตรวจสัญญาข้อมูล แยกวันเวลา คำนวณแคลอรีจากแหล่งอ้างอิง คัดส่วนผสม จัดตาราง และตรวจสิทธิ์ร่วมกับ AI ห้าม merge adapter แล้วใช้ทุกงาน หรือเพิ่มคำสั่งให้โมเดลข้าม validation

ข้อความผู้ใช้เข้า `POST /api/chat` ระบบเลือกตอบวิธีใช้ ข้อมูลที่ผู้ใช้นั้นยืนยันแล้ว แนะนำเมนู คำนวณแคลอรี เตรียมบันทึก/แก้/ลบ เสนอตาราง หรือความรู้สุขภาพตามคำถาม คำถามทั่วไปที่นอกสุขภาพและเบาหวานจะถูกปฏิเสธ คำถาม “ถามอะไรได้บ้าง” เป็นวิธีใช้งาน ต้องตอบได้ คำถาม “กินข้าวกับอะไรดี” เป็นขอแนะนำอาหาร ต้องไม่สร้างบันทึก “วันนี้กินอะไรไปบ้าง” อ่านประวัติ ส่วน “กินข้าวกับไข่พะโล้” เตรียมร่างมื้อเดียว

ความรู้สุขภาพใช้หลักฐาน RAG และช่องค้น MedlinePlus ที่ควบคุมไว้ แสดง citation ที่ API ส่งมา ไม่สร้าง URL/ชื่อแหล่งเอง ไม่ส่งชื่อหรือประวัติสุขภาพไปค้นเว็บ และไม่เปิดให้โมเดลรัน SQL, shell, JavaScript หรือเรียก URL ตามข้อความที่ผู้ใช้ให้

## เชื่อมต่อโดยรักษาบัญชีเดิม

- Browser เรียก backend ของเว็บไซต์เดิม แล้ว backend จึงเรียก `http://127.0.0.1:8765/api/...` บนเครื่องที่รันบริการ AI กุญแจ `RUAMWAN_API_KEY` อยู่ใน environment ฝั่ง server เท่านั้น ห้ามใช้ตัวแปร public เช่น `NEXT_PUBLIC_`/`VITE_` หรือส่งกุญแจให้ browser
- ทุก request จาก backend ส่ง `Authorization: Bearer <RUAMWAN_API_KEY>` และ `X-Ruamwan-User: <stable opaque user ID>` ID ต้องได้จาก login ที่ backend ตรวจแล้ว เช่น `my-site:<auth-subject>` ห้ามเชื่อ userId/owner จาก body, query หรือ header ของ browser ต้องใส่ namespace ของเว็บ/tenant เพื่อไม่ให้ ID ชน
- ใช้ client ที่แนบกับ runtime ที่รองรับ backend Node.js 20+ หรือเขียน client ตาม OpenAPI หากใช้ภาษาอื่น ตัวอย่าง client ไม่ได้เป็น login server ให้ใช้ระบบ login/authorization เดิม ไม่ต้องเปลี่ยนระบบบัญชี
- API แยกเจ้าของและผูกบัญชีถาวรในฐานข้อมูลของบริการ ไม่ต้องเรียก `/api/session` ใน server integration โหมดเดโม cookie+CSRF ยังใช้ได้ แต่ห้ามนำ cookie เดียวไปแชร์ทุกบัญชี
- การรัน AI ต้องอยู่บน Mac Apple Silicon ที่ติดตั้ง runtime นี้ browser โหลด weights โดยตรงไม่ได้ ถ้าเว็บอยู่บน Vercel ให้ใช้ HTTPS gateway ตาม docs/vercel-gateway.md และ integration/gateway.json ตั้ง RUAMWAN_GATEWAY_URL กับ RUAMWAN_API_KEY เฉพาะ server แล้วใช้ option gatewayUrl ใน client รุ่นปัจจุบัน ห้าม fallback ไป localhost บน Vercel URL ปัจจุบันเป็น Quick Tunnel ชั่วคราว ไม่ใช่ production ถาวร ห้ามอ้างว่า MLX ชุดนี้ติดตั้งบน Linux ได้ทันที

## สัญญาการแชตและปุ่มสั่งงาน

ส่ง `messages` เป็นบทสนทนา role `user`/`assistant` และ `scope:"auto"` พร้อม `captured_at` เป็น ISO timestamp ที่มี timezone ของเวลาที่ส่งข้อความ เช่น `new Date().toISOString()` กำหนด timestamp ครั้งเดียวต่อข้อความ เก็บใช้ซ้ำระหว่างเตรียม/ตรวจ/ยืนยัน แม้ผู้ใช้กดยืนยันหลังเที่ยงคืน อย่าสร้าง timestamp ใหม่เมื่อกดปุ่มแก้รายละเอียดของข้อความเดิม ถ้าไม่ส่ง API ใช้เวลารับคำขอ

แสดง `answer` เป็นข้อความที่ escape แล้ว ไม่แทรก HTML ดิบ แสดง `suggestions` เป็นคำถามลัด และ `citations`/`record_sources` ตามที่ API ส่งมา ชื่อและรูปทรง field ให้ยึด OpenAPI/ผลจริง แยก loading, empty, timeout, retry, error และยกเลิก request เมื่อ reset/logout ไม่ให้คำตอบบัญชีเก่ามาปรากฏในบัญชีใหม่

รองรับ `actions[]` แบบ allowlist เท่านั้น:

| type | พฤติกรรมในเว็บเดิม |
| --- | --- |
| `navigate` | map page `overview/profile/record/plan/chat/knowledge` ไป route เดิมของเว็บ ห้ามให้ AI ส่ง URL แล้วเปิดได้ทุกที่ |
| `records` | แสดงและแก้ `records` ก่อนส่ง batch-preview รองรับ `inline`, `before`, `compact` ถ้ามี |
| `journal` | ใส่ `text` ในช่องบันทึกเดิม ใช้ `captured_at` ที่ action ส่งมา แล้วเรียก journal/prepare |
| `plan` | เรียก plans/preview ด้วย start_date และแสดงผลตรวจตารางก่อนยืนยัน |
| `delete_records` | แสดงรายการและผลกระทบ เรียก delete-preview ตาม scope/record_ids แล้วให้ผู้ใช้ยืนยัน |
| `export` | ดาวน์โหลดข้อมูลของบัญชีปัจจุบันจาก API หลังผู้ใช้กด |

ไม่รู้จัก action ใดให้ข้ามอย่างปลอดภัย อย่าแสดง error แทนคำตอบทั้งก้อน ห้าม AI หรือ frontend auto-confirm เพราะพบ action ในคำตอบ ผู้ใช้ต้องกดปุ่มเอง

## การบันทึกที่ไม่ต้องกรอกเยอะ

ใช้ `POST /api/journal/prepare` กับ `{text,captured_at,compact:true}` รับ `items[].record`, `items[].check`, `warnings` และ `unparsed` ผู้ใช้เล่าหลายหมวดในข้อความเดียวได้ จัดกลุ่มเป็นการ์ดสั้นในพื้นที่บันทึกเดิม ให้ตรวจชื่อ เวลา ปริมาณ แก้หมวด หรือไม่เลือกรายการได้ ไม่มีรายการที่แยกได้ต้องบอกตามจริง ห้ามใช้ข้อความ unparsed เป็นบันทึกโดยไม่ให้เลือกหมวดและตรวจเอง

- ไม่บอกวัน → วันที่ไทย ณ เวลาที่พิมพ์ ไม่ใช้วันตอนยืนยัน
- ไม่บอกเวลา/ช่วงเวลา → ใช้เวลาที่พิมพ์ ระดับนาที แสดง “เวลาที่พิมพ์ · แก้ได้” โดย `journal.clock_source="capture_time"` ห้ามอ้างว่าเป็นเวลาเกิดเหตุที่ผู้ใช้ระบุ
- บอก “ตอนเช้า/เที่ยง/บ่าย/เย็น/กลางคืน” → เก็บ period ที่บอก ไม่สร้างเวลาเป๊ะ clock=null ใช้ได้แม้ยังไม่เติมเวลา
- บอก “16.00” → เก็บ 16:00 source=explicit คำทศนิยมเช่น “น้ำหนัก 16.00 กก.” ไม่ใช่เวลา
- แก้เวลาเอง → clock_source=user_edited และปรับ `data.occurred_at` หรือ `data.start` ให้ตรง journal.date/clock พร้อม timezone ห้ามเปลี่ยน captured_at เดิม
- กิจกรรม/นอน/นัดหมาย: เติมแค่ start เมื่อใช้เวลาที่พิมพ์ ไม่แต่ง end หรือระยะเวลา ถ้าข้อมูลไม่ครบแสดงว่ายังไม่ครบ ไม่คิดเป็น 0 นาที
- ยา: เวลาเป็นเพียงค่าเริ่มต้นของบันทึก ไม่พิสูจน์ว่ากินแล้ว ไม่อนุมานขนาด/ความถี่/แผนรักษา

บันทึกเป็นชื่อสั้นและค่าแยกช่อง ไม่เก็บย่อหน้าเล่ายาวใน record เมื่อใช้ compact=true อย่าตัดชื่อเมนูครึ่งคำ ข้อมูลที่ไม่ทราบเป็น null/unknown ไม่ใส่ 0 แทน และไม่เติมแพ้/โรค/ปริมาณให้เอง

## อาหารและแคลอรี

อาหารหนึ่งมื้อมีหลายส่วนได้ เช่น “ข้าวกับไข่พะโล้” เป็น record kind=meal เดียว `data.components` เก็บข้าวและไข่พะโล้คนละชื่อ/quantity/unit/food_state ห้ามแยกนับเป็นสองมื้อหรือคูณปริมาณระดับมื้อกับทุกส่วน ห้ามบวกข้าวซ้ำให้เมนูที่มีข้าวอยู่แล้ว เช่นข้าวมันไก่

แสดง `items[].check.calculated.energy` ข้างอาหาร ใช้ `POST /api/food-energy` คำนวณใหม่เมื่อแก้ชื่อ/ปริมาณ/หน่วย/components ส่งเฉพาะ fields ตาม FoodEnergyRequest ไม่ส่ง occurred_at หรือ record ทั้งก้อน เมื่อแก้แล้วล้างค่าพลังงานเก่าทันทีและกัน response เก่าทับค่าใหม่

แสดงช่วง kcal, หน่วยเสิร์ฟ/basis, assumed_portion และแหล่งอ้างอิง หาก partial ต้องแสดง “ยังรวมไม่ครบ” หาก unknown/null ให้แสดง “ยังประเมินไม่ได้” ไม่ตีเป็น 0 หรือสร้างเลขจาก AI ยอดวันนี้อ่าน `GET /api/summary` ที่ `energy_summary` รวมเฉพาะมื้อที่ยืนยันแล้ว การแก้/ลบต้อง refresh summary และประวัติ

การแนะนำเมนูใช้ `menus`/`details`/`meal_references` ของ API รักษาการคัดส่วนผสมแพ้และข้อจำกัดแต่ละคน แสดงข้อจำกัดที่เกี่ยวข้องอย่างกระชับ ไม่ยัดข้อความ BMI/ยาในคำตอบทุกครั้ง ไม่ตั้งเป้าลดน้ำหนักหรือแคลอรีรักษาโรคเอง

## ลำดับเขียน แก้ไข ลบ และแผน

1. รับร่าง/แก้ฟอร์ม แล้วส่ง `POST /api/records/batch-preview` `{records,compact:true}` หรือ records/preview สำหรับรายการเดียว ตรวจ `checks`, `can_confirm`, `requires_consent`
2. หากต้องให้ consent แสดงช่องให้ผู้ใช้เลือกเอง แล้วเพิ่ม record `{kind:"consent",data:{local_storage:true},source:"ผู้ใช้ให้ความยินยอมผ่านเว็บไซต์"}` ใน batch และ preview ใหม่ ห้ามติ๊กไว้เอง
3. หลังผู้ใช้กดยืนยัน เรียก `/api/confirm` ด้วย `{draft_id,idempotency_key,confirmed:true}` key เป็น UUID ใหม่ต่อการทำรายการ แต่ใช้ key เดิมเมื่อ retry คำขอยืนยันเดิม ห้าม retry อัตโนมัติหลังเปลี่ยน payload
4. แก้ record โดยใช้ `previous_id` ของเวอร์ชันที่แก้ ผ่าน preview/confirm ไม่เขียนทับประวัติหรือสร้าง ID เอง ถ้ารายการเปลี่ยนพร้อมกันให้โหลดใหม่และตรวจอีกครั้ง
5. ลบผ่าน `/api/records/delete-preview` แล้ว `/api/confirm` แสดงจำนวนรายการ/เวอร์ชันและแผนที่กระทบ ผู้ใช้ยืนยันลบเอง
6. แผนใช้ routine+constraint ที่ยืนยันแล้ว เรียก `/api/plans/preview` ไม่ใช้ข้อความที่ AI แต่งเป็นเวลาจริง แสดงปัญหาเวลาชนและ can_confirm ยา/นัดหมายล็อกตามคำสั่งเดิม ไม่เปลี่ยนยาเอง
7. หลังสำเร็จ refresh records/summary/plans ตามผล ห้ามบอก “บันทึกแล้ว” ก่อน API ยืนยันสำเร็จ draft หมดอายุประมาณ 30 นาที/หลัง server restart ต้อง preview ใหม่ การ confirm สำเร็จแต่เครือข่ายขาดให้ retry ด้วย draft/key เดิมตามสัญญา

## ข้อมูลและการย้ายข้อมูล

อ่าน OpenAPI สำหรับ fields ทั้งหมด Profile เก็บข้อมูลเท่าที่ทราบ เช่น age, weight_kg, height_cm, conditions, medications, allergies, preferences, goals, mobility_limits, reported_type2, pregnant, complex_care, timezone ค่า allergies=null คือยังไม่ทราบ ส่วน [] คือผู้ใช้ยืนยันว่าไม่มีการแพ้ที่ทราบ ห้ามสลับกัน

บันทึกรองรับ meal/activity/sleep/medication/appointment/measurement/wellbeing พร้อม journal metadata และ origin/source ส่วนการจัดตารางใช้ routine/constraint/feedback ค่าตรวจต้องมีชนิด/หน่วย/context/method ไม่เทียบค่าต่างเงื่อนไขเป็นแนวโน้มเดียวกัน

ระบบ login/บัญชีและโครงสร้างฐานข้อมูลเว็บไซต์เดิมคงไว้ บริการ AI ใช้ฐานข้อมูลของตัวเองเป็นหลักสำหรับข้อมูลสุขภาพที่ API อ่าน ถ้าเว็บมีข้อมูลเดิม ให้ทำ mapping fields ที่ทราบแน่นอนและ import ผ่าน preview/confirm โดยผู้ใช้ยินยอมก่อน อย่าคัดลอกประวัติจริงลง prompt/training ห้ามให้เว็บไซต์กับ AI เขียนสำเนาข้อมูลคนละชุดอิสระจนยอดไม่ตรงกัน หากต้องมี cache/projection ในเว็บ ให้ refresh จาก API หลัง confirm และเก็บ server record id/version เป็นตัวเชื่อม ไม่ให้ cache กลายเป็นข้อมูลสุขภาพหลักอีกชุด

ไม่รวมฐานข้อมูลผู้ใช้หรือ secret ใน bundle ใช้ persistent LOCAL_DB และสำรองทั้งข้อมูลกับ integration_accounts mapping เพื่อคืนสิทธิ์บัญชีเดิม บริการนี้ยังต้องมีการจัดการ backup/restore, quota/rate limiting, TLS gateway และนโยบายข้อมูลของเว็บไซต์ก่อนเปิดต่อสาธารณะ อย่าอ้าง clinical validation หรือรับประกันว่าไม่มีข้อผิดพลาด

## เกณฑ์ที่ต้องทดสอบบนเว็บไซต์จริง

- “กินข้าว” ได้ร่างเวลา ณ ตอนส่ง (เวลาประเทศไทย) และไม่เขียนก่อนยืนยัน
- “ตอนเช้ากินข้าว” มีช่วงเช้าและ clock=null; “เดิน 16.00” ได้16:00 ไม่มี end ที่แต่งขึ้น
- “กินข้าวกับอะไรดี” แนะนำเมนู ไม่เปิดร่าง; “วันนี้กินอะไรไปบ้าง” อ่านเฉพาะประวัติ
- “กินข้าวกับไข่พะโล้” เป็นมื้อเดียว components สองอย่าง แก้ปริมาณได้ ยอดไม่ซ้ำ
- unknown calories ไม่เป็น0; partial แสดงว่ายังไม่ครบ; ที่มาเปิดได้และไม่มี URL ที่ AI แต่ง
- วิธีใช้ตอบสั้นพร้อมตัวอย่าง; นอกประเด็นปฏิเสธ; งานสุขภาพที่หลักฐานไม่พอแจ้งตรงไปตรงมา
- edit/delete cancel แล้วข้อมูลเดิมอยู่; confirm แล้วประวัติ/summary เปลี่ยน; retry ไม่ซ้ำ
- บัญชี A อ่าน/แก้/ยืนยัน draft ของ B ไม่ได้ เปลี่ยน login/logout แล้วล้างแชต/ร่างเดิม
- คีย์อยู่เฉพาะ server, ไม่มีใน frontend bundle/devtools/network browser; userId ได้จาก verified login
- API ปิด/โมเดลไม่พร้อม/429/422/timeout แสดงข้อความที่ทำต่อได้ ไม่ลบข้อความที่พิมพ์ ไม่บันทึกเอง
- มือถือ/คีย์บอร์ด/ตัวหนังสือใหญ่ใช้งานได้ โดย layout และ navigation เดิมยังอยู่

เมื่อเสร็จ ส่งตาราง mapping ไฟล์ที่แก้ ผลทดสอบที่รันจริง คำสั่งเปิดระบบ และส่วนที่ยังต้องตั้งค่าบน host ของฉัน ไม่ต้องสร้างข้อมูลฝึกหรือเทรนโมเดลใหม่เพื่อเชื่อมเว็บครั้งนี้
