ช่วยสร้างโปรเจกต์ AI สำหรับแอปดูแลสุขภาพและวางแผนกิจวัตรเฉพาะบุคคล โดยลงมือสร้างไฟล์ เตรียมข้อมูล ฝึกโมเดล ประเมิน และสาธิตการทำงานจริงตามข้อกำหนดนี้

แอปต้องครอบคลุมอาหาร การออกกำลังกาย การนอน การใช้ยาและนัดหมาย การติดตามสุขภาพ และการสนับสนุนพฤติกรรม โดยเชื่อมทุกด้านเป็นแผนเดียวกัน ไม่ทำเป็นระบบอาหารที่มีฟังก์ชันอื่นเพียงเล็กน้อย

อ่านข้อกำหนดทั้งหมดก่อนเริ่ม จัดทำแผนงานสั้น ๆ แล้วดำเนินการต่อ ไม่หยุดแค่เสนอแผน ไม่ส่งเพียง pseudocode และไม่รายงานความสำเร็จที่ไม่ได้ทดลองจริง

# 1. เครื่อง โมเดล และงบเวลา

เครื่องเป้าหมาย:
- Mac Apple M4
- Unified Memory 16 GB
- macOS
- เตรียมข้อมูล ฝึก และ inference บนเครื่องนี้
- ไม่ใช้ Colab, CUDA, bitsandbytes หรือ GPU ภายนอก

โมเดลหลัก:
- typhoon-ai/typhoon2.5-qwen3-4b
- ใช้ MLX-LM และ LoRA บนโมเดล quantized 4-bit
- ตรวจ model card, license, revision, tokenizer, chat template และการรองรับของ MLX-LM รุ่นที่ติดตั้งจริง
- อ่านเอกสารทางการก่อนเลือกคำสั่ง อย่าใช้ flags จากความจำโดยไม่ตรวจ
- ไม่อ้างว่า MLX quantized LoRA มีรายละเอียดเหมือน QLoRA บน CUDA ทุกประการ
- หากจำเป็นต้องเปลี่ยนโมเดลหรือวิธีฝึก ให้อธิบายหลักฐานและผลกระทบก่อน

ตั้งเป้าต้นแบบภายในประมาณ 24 ชั่วโมง รวม:
- ตรวจสภาพแวดล้อม
- ตรวจสิทธิและเตรียมข้อมูล
- สร้างระบบหลัก
- ฝึกจริง
- ประเมินและสาธิต

บันทึกเวลาเริ่มและเวลาที่ใช้จริง กันเวลาอย่างน้อย 2 ชั่วโมงสำหรับประเมิน โหลด adapter กลับมา และตรวจส่งมอบ

กำหนดจำนวนตัวอย่างและ training steps จาก pilot ไม่บังคับฝึกให้ครบ 24 ชั่วโมง และไม่รับประกันว่า fine-tuning จะดีกว่าโมเดลฐาน

หากงานทั้งหมดไม่พอเวลา ให้ลดความซับซ้อนของ UI การค้นหาแบบขั้นสูง และการทดลองหลาย configuration ก่อนลดการตรวจข้อมูลหรือการประเมิน

# 2. กลุ่มผู้ใช้และนิยามความสำเร็จ

กลุ่มผู้ใช้ระยะแรก:
ผู้ใหญ่ในประเทศไทยที่เป็นเบาหวานชนิดที่ 2 และต้องการจัดกิจวัตรให้เข้ากับชีวิต สุขภาพ และข้อจำกัดของตน

ผู้ใช้แต่ละคนอาจแตกต่างกันด้าน:
- น้ำหนัก ส่วนสูง และรอบเอว
- ค่าตรวจสุขภาพและโรคร่วม
- ยาและคำแนะนำจากผู้ดูแล
- สมรรถภาพและข้อจำกัดการเคลื่อนไหว
- เวลางานและการทำงานเป็นกะ
- เวลานอน ความเหนื่อยล้า และภาระครอบครัว
- ความชอบอาหาร งบประมาณ และการเข้าถึงอาหาร
- เป้าหมาย ความพร้อม และอุปสรรคในการเปลี่ยนพฤติกรรม

ความสำเร็จของต้นแบบ:
1. รับและตรวจข้อมูลผู้ใช้ได้
2. บันทึกกิจกรรมหลายด้านโดยให้ผู้ใช้ยืนยัน
3. ตอบคำถามพร้อมหลักฐานที่ค้นได้จริง
4. เสนอแผน 7 วันจากกิจกรรม เป้าหมาย และข้อจำกัดที่ยืนยันแล้ว
5. ตรวจความขัดแย้งของแผนด้วยโปรแกรม
6. เสนอปรับแผนจากข้อจำกัดใหม่และผลตอบรับ
7. อธิบายได้ว่าใช้ข้อมูลและหลักฐานใด
8. มีการฝึกและประเมินโมเดลจริง หากมีข้อมูลที่ผ่านเกณฑ์
9. แยกสิ่งที่พร้อมใช้ สิ่งที่ยังขาดข้อมูล และสิ่งที่รอผู้เชี่ยวชาญตรวจ

“ครอบคลุม” หมายถึงรองรับกระบวนการของทุกด้าน ไม่ได้หมายถึงให้คำแนะนำเฉพาะโรคได้ทุกภาวะ

ห้ามอ้างว่ารองรับทุกโรค เด็ก หญิงตั้งครรภ์ หรือกลุ่มซับซ้อน หากยังไม่มีหลักฐาน กฎ และการประเมินที่ตรงกลุ่ม

# 3. สถาปัตยกรรมและการแบ่งหน้าที่

แยกส่วนต่อไปนี้ให้ทดสอบได้อิสระ:

1. โมเดลภาษา
   - เข้าใจข้อความ
   - สรุปข้อมูล
   - เสนอข้อมูลที่ต้องถามเพิ่ม
   - เสนอทางเลือกจากรายการที่ระบบอนุญาต
   - อธิบายแผนและหลักฐาน

2. RAG
   - ค้นคำแนะนำจากเอกสารที่ตรวจแหล่งที่มาแล้ว
   - คืนข้อความรองรับพร้อมรหัสเอกสารและตำแหน่ง
   - ไม่ใช้คำตอบที่โมเดลจำได้แทนการอ้างอิง

3. Rule engine
   - ตรวจเงื่อนไข ข้อมูลที่จำเป็น และข้อจำกัด
   - แยกกฎทางโปรแกรมจากกฎทางสุขภาพ
   - กฎสุขภาพที่ยังไม่ผ่านการทบทวนต้องไม่แสดงว่าได้รับการรับรอง

4. Scheduler
   - จัดกิจกรรมลงเวลา
   - เคารพข้อจำกัดที่เปลี่ยนไม่ได้
   - รายงานกรณีจัดแผนไม่ได้

5. เครื่องคำนวณ
   - คำนวณสารอาหาร
   - แปลงหน่วย
   - คำนวณระยะเวลาและสรุปกิจกรรม
   - ใช้สูตรและข้อมูลที่ตรวจสอบได้

6. Backend และฐานข้อมูล
   - ตรวจรูปแบบข้อมูลและสิทธิผู้ใช้
   - บันทึกหลังการยืนยัน
   - เก็บ provenance และ audit
   - เตรียมเชื่อม Supabase

ไม่ให้ LLM เป็นผู้คำนวณ ผู้ตรวจข้อจำกัด และผู้ตัดสินความเหมาะสมทางสุขภาพเพียงตัวเดียว

ใช้ workflow ที่ชัดเจนก่อน ไม่จำเป็นต้องสร้าง autonomous agent หลายตัว

# 4. ข้อมูลจริงและข้อห้ามเรื่องข้อมูลฝึก

ห้ามเพิ่มข้อมูลฝึกที่แต่งขึ้นหรือใช้ AI สร้าง:
- ผู้ป่วยและประวัติสุขภาพสมมติ
- ค่าตรวจหรือผลลัพธ์สุขภาพสมมติ
- คำถาม–คำตอบจาก LLM
- แผนอาหาร กิจกรรม หรือการนอนที่ AI สร้างแล้วนำกลับไปฝึก
- สูตรอาหาร ปริมาณ หรือค่าสารอาหารที่เดา
- คำแนะนำที่จับคู่กับคนละบุคคลเพราะลักษณะคล้ายกัน
- การแปลและ paraphrase ด้วย AI เพื่อเพิ่มจำนวน
- การเติมค่าที่ขาดจากบุคคลอื่นโดยไม่ระบุวิธีและเหตุผล

อนุญาต:
- แปลงข้อมูลต้นฉบับเป็นรูปแบบ messages
- คัดกรองและลบข้อมูลซ้ำ
- แปลงหน่วยด้วยสูตรที่ตรวจได้
- คำนวณตัวแปรจากข้อมูลจริง โดยเก็บสูตรและค่าต้นฉบับ
- สร้าง schema และตัวนำเข้าข้อมูล

ทุกตัวอย่างฝึกต้องย้อนกลับไปยังแหล่ง ไฟล์ เอกสาร และแถวหรือรหัสต้นฉบับได้

แยกให้ชัด:
- ข้อมูลวัดจริง
- ข้อมูลผู้เข้าร่วมรายงานเอง
- ค่าประมาณจากอุปกรณ์
- ค่าคำนวณ
- คำแนะนำจากผู้เชี่ยวชาญ
- ข้อเสนอจากโมเดล

ข้อกำหนดนี้ใช้กับข้อมูลที่เพิ่มในโครงการ ไม่อ้างว่ารับรองข้อมูล pretraining ทั้งหมดของ Typhoon ได้

การทดสอบโปรแกรมอาจใช้ fixture ที่สร้างขึ้นเพื่อทดสอบความผิดพลาด แต่ต้องติดป้ายว่าเป็น software test ไม่ใช่ผู้ป่วยจริง และห้ามนำเข้า training หรือใช้เป็นหลักฐานความถูกต้องทางคลินิก

# 5. ตรวจ dataset และหลักฐานอย่างเป็นระบบ

สร้าง dataset/source manifest โดยมี:
- ชื่อและผู้จัดทำ
- URL ต้นทาง
- version หรือ revision
- วันที่เข้าถึงและ hash ไฟล์
- license และขอบเขตสิทธิที่ตรวจได้
- จำนวนแถว จำนวนบุคคล และจำนวนตัวอย่างที่ใช้จริง
- ตัวแปร หน่วย ช่วงเวลา และวิธีเก็บข้อมูล
- missing codes
- บทบาทในระบบ
- ข้อจำกัดและเหตุผลที่คัดออก

ใช้สถานะอย่างน้อย:
- candidate
- downloaded
- inspected
- eligible
- used
- excluded
- access_pending

ห้ามนับแหล่งที่เพียงอ่านหน้าเว็บว่าเป็นข้อมูลที่ใช้ฝึกแล้ว

แยกสิทธิสำหรับ:
- ดาวน์โหลดและประมวลผล
- ฝึกโมเดล
- ใช้ในระบบค้นข้อมูล
- แจกจ่ายข้อมูล
- แจกจ่าย adapter หรือผลลัพธ์ที่เกี่ยวข้อง

การอ่านได้ฟรีไม่แปลว่ามีสิทธิทุกอย่าง

# 7. โปรไฟล์และข้อมูลผู้ใช้

ออกแบบข้อมูลเป็นหมวด:

## 7.1 ข้อมูลพื้นฐาน
- อายุหรือวันเกิดตามความจำเป็น
- เขตเวลา
- น้ำหนัก ส่วนสูง รอบเอว พร้อมวันที่และหน่วย
- ข้อมูลอื่นเมื่อมีเหตุผลต่อการใช้งาน

ไม่เก็บทุกอย่างเพียงเพราะอาจใช้ได้ในอนาคต

## 7.2 สุขภาพและแผนรักษา
- ภาวะที่ผู้ใช้รายงาน
- ค่าตรวจพร้อมหน่วย เวลา และบริบท
- ยาและคำสั่งใช้ที่ยืนยัน
- เป้าหมายและข้อจำกัดจากผู้ดูแล
- แหล่งที่มาของแต่ละรายการ
- ช่วงเวลาที่ข้อมูลยังใช้ได้ หากกำหนดไว้

แยก “ผู้ใช้รายงาน” ออกจาก “มีเอกสารยืนยัน” และ “ผู้ดูแลตรวจแล้ว”

## 7.3 ตารางชีวิต
- เวลางานและงานเป็นกะ
- การเดินทาง
- ภาระประจำ
- ช่วงนอน
- เวลามื้ออาหาร
- เวลาว่าง
- กิจกรรมที่เปลี่ยนไม่ได้

## 7.4 ความชอบและทรัพยากร
- อาหารและกิจกรรมที่ชอบ
- การแพ้อาหารและสิ่งที่หลีกเลี่ยง
- งบประมาณเมื่อมีข้อมูล
- อุปกรณ์และสถานที่
- ความสามารถทำอาหารและการเคลื่อนไหว
- ความต้องการเรื่องการแจ้งเตือน

## 7.5 เป้าหมายและผลตอบรับ
- เป้าหมายที่ผู้ใช้ยืนยัน
- ความพร้อมและอุปสรรค
- เหตุผลที่ทำหรือไม่ทำกิจกรรม
- ความยาก ความเหนื่อยล้า และความพึงพอใจ

ไม่กำหนดแผนจากน้ำหนักหรือ BMI เพียงอย่างเดียว และไม่ต้องฝึกโมเดลใหม่แยกให้ผู้ใช้แต่ละคน ใช้โปรไฟล์ล่าสุดในการวางแผนตอน inference

# 8. การบันทึกและตรวจข้อความ

รองรับข้อความเกี่ยวกับ:
- อาหาร
- กิจกรรม
- การนอน
- การใช้ยาที่ผู้ใช้รายงาน
- ค่าตรวจ
- อุปสรรคและผลตอบรับ

กระบวนการ:
1. โมเดลเสนอข้อมูลที่แยกได้
2. ตรวจ schema ชนิดข้อมูล หน่วย และเวลา
3. ระบุข้อมูลกำกวม ขาด หรือขัดแย้ง
4. แสดงให้ผู้ใช้ตรวจและแก้
5. Backend บันทึกหลังยืนยัน
6. เก็บประวัติการแก้ไข

แต่ละ field ควรอ้างถึงข้อความส่วนที่รองรับเมื่อทำได้ และใช้ null สำหรับค่าที่ไม่พบ

ตัวอย่างสิ่งที่ต้องตรวจ:
- น้ำตาลไม่มีหน่วยหรือบริบทการวัด
- เวลาเข้านอนและตื่นนอนข้ามวัน
- ปริมาณอาหารไม่ชัด
- กิจกรรมไม่มีระยะเวลา
- คำสั่งยาสองรายการไม่ตรงกัน
- เวลาว่างชนกับเวลางาน
- ข้อมูลเก่าขัดกับข้อมูลใหม่

ข้อขัดแย้งบางอย่างต้องถามเพิ่ม ไม่ใช่ให้โมเดลเลือกว่าข้อมูลใดถูกเอง

ไม่ให้โมเดลเขียนฐานข้อมูลโดยตรง ไม่สร้าง SQL จากข้อความผู้ใช้แล้วรัน และไม่ให้สิทธิ service role กับโมเดล

- ถ้าไม่มีราคา ไม่อ้างว่าผ่านงบ

## ค่าตรวจ

- ตารางที่เปลี่ยนไม่ได้
- กิจกรรมและรายการอาหารที่มีข้อมูลรองรับ
- ข้อจำกัดจากผู้ใช้และผู้ดูแล
- กฎที่เปิดใช้งานได้
- ผลตอบรับที่ผ่านมา

แยก:

Hard constraints:
- เวลางาน นัดหมาย และกิจกรรมที่ล็อก
- เงื่อนไขยาที่กำหนด
- ข้อห้ามและข้อจำกัดที่ยืนยัน
- กิจกรรมไม่ซ้อนกัน
- ข้อมูลจำเป็นต้องครบสำหรับข้อเสนอชนิดนั้น

Soft preferences:
- เวลาและกิจกรรมที่ชอบ
- ความหลากหลาย
- ความสะดวก
- การเปลี่ยนจากแผนเดิมให้น้อย
- งบประมาณเมื่อมีข้อมูลราคา

ความต้องการแบบ soft ต้องไม่ชนะ hard constraints

ขั้นตอน:
1. ตรวจความพร้อมของข้อมูลแยกตามด้าน
2. ถามเฉพาะข้อมูลที่มีผลต่อการตัดสินใจ
3. เลือกกิจกรรมจากรายการที่อนุญาต
4. ใช้ scheduler จัดเวลา
5. ใช้ calculator และ rule engine ตรวจ
6. ให้โมเดลอธิบายผลจากข้อมูลที่ตรวจแล้ว
7. ตรวจข้อความสุดท้ายว่าตรงกับแผนและตัวเลข
8. ให้ผู้ใช้เลือกหรือแก้ไข
9. บันทึกเป็นแผนเวอร์ชันใหม่หลังยืนยัน

แต่ละ plan item ต้องมี:
- ประเภทกิจกรรม
- วัน เวลา และระยะเวลาเมื่อเกี่ยวข้อง
- รายการที่เลือกและปริมาณเมื่อมี
- เป้าหมายที่เกี่ยวข้อง
- ข้อมูลผู้ใช้ที่รองรับ
- source/rule IDs
- ผลตรวจ
- ข้อมูลที่ยังขาด
- สถานะการยืนยัน

ผลตรวจต้องแยก:
- pass
- fail
- unknown
- not_applicable

ห้ามตีความ unknown ว่าผ่าน

หากจัดแผนไม่ได้ ให้แสดงข้อจำกัดที่ขัดกันและทางเลือกที่ผู้ใช้ตัดสินใจได้ ไม่แก้ hard constraints เองและไม่เติมกิจกรรมเพื่อให้ครบ 7 วันอย่างไร้เหตุผล

# 14. การปรับแผนจากผลติดตาม

ใช้:
- ข้อจำกัดใหม่
- เหตุผลที่ผู้ใช้แจ้ง
- กิจกรรมที่ยืนยันว่าทำจริง
- ความพึงพอใจ ความเหนื่อยล้า และความพร้อม
- ข้อมูลสุขภาพที่ตีความได้ตามกฎที่รองรับ

เริ่มจากเสนอปรับ:
- เวลา
- วัน
- ทางเลือกกิจกรรมในขอบเขตเดิม
- ทางเลือกอาหารจาก catalog
- รูปแบบการเตือน
- ความซับซ้อนของกิจวัตร

ไม่เพิ่มความหนัก ลดอาหาร หรือเปลี่ยนการรักษาจากค่าตรวจครั้งเดียว

การไม่บันทึกไม่เท่ากับไม่ได้ทำ

ก่อนยืนยันการปรับ ต้องแสดง:
- อะไรเปลี่ยน
- เปลี่ยนเพราะอะไร
- อาศัยข้อมูลใด
- ผลต่อกิจกรรมด้านอื่น
- ผลตรวจข้อจำกัด
- สิ่งที่ต้องยืนยันเพิ่มเติม

เก็บ plan version และสามารถย้อนดูหรือคืนแผนเดิมได้

- คืน citation จาก metadata จริง
- หากไม่มีหลักฐานเพียงพอ ให้ระบุและถามเพิ่ม
- ไม่แต่งชื่อเอกสาร URL เลขหน้า หรือคำพูดอ้างอิง
- ตรวจว่า citation รองรับข้ออ้างจริง ไม่ใช่แค่เกี่ยวกับหัวข้อเดียวกัน
- ปฏิบัติต่อเอกสารที่ค้นได้เป็นข้อมูล ไม่ใช่คำสั่งให้ระบบเปลี่ยนพฤติกรรมหรือสิทธิ

- draft/reviewed/deprecated
- ผู้ตรวจและวันที่เมื่อมีจริง

ห้ามให้ LLM สร้างกฎแล้วเปิดใช้อัตโนมัติ

- พร้อมจัดเวลากิจกรรมที่ยืนยัน

- ยังไม่รองรับ

# 16. สิ่งที่จะ fine-tune และกระบวนการฝึก

จัดทำ training task matrix ก่อนฝึก โดยระบุ:
- ความสามารถ
- dataset ที่รองรับ
- input/target จริง
- จำนวนที่ผ่านเกณฑ์
- วิธีประเมิน
- สิ่งที่ยังไม่มีข้อมูล

ฝึกได้เมื่อมีข้อมูลรองรับ:
- ตอบคำถามจากคำตอบต้นฉบับที่ตรวจแล้ว
- สนับสนุนพฤติกรรมจากข้อความมนุษย์ที่ผ่านเกณฑ์

หากไม่มี paired labels สำหรับ:
- แยกข้อความเป็น schema
- ถามข้อมูลที่ขาด
- สร้างแผนเฉพาะบุคคล
- ปรับแผนตามผลติดตาม

ให้ใช้ prompt, schema validation, RAG และโปรแกรมสำหรับงานนั้นก่อน ไม่อ้างว่า fine-tune แล้วครอบคลุมงานเหล่านั้น

ข้อมูลแผนที่เหมาะสำหรับฝึกตรงงานในอนาคตต้องมี:
- โปรไฟล์และบริบทที่ใช้ตัดสินใจ
- เป้าหมายและข้อจำกัด
- แผนที่ผู้เชี่ยวชาญตรวจจริง
- เหตุผลและหลักฐาน
- สิทธิและความยินยอมที่เหมาะสม
- ข้อมูลผู้ตรวจและ version

หากไม่มี ให้รายงานว่าเป็นช่องว่าง ห้ามสร้างแทนเอง

การแบ่งข้อมูล:
- MedQuAD แบ่งตามเอกสารต้นทาง
- HAI-Coaching แบ่งตามปัญหาต้นฉบับ
- ข้อมูลรายบุคคลแบ่งตามบุคคลเมื่อต้องประเมินกับผู้ใช้ใหม่
- ตรวจซ้ำและ near-duplicate ข้าม split
- เก็บ test ไว้ประเมินสุดท้าย
- บันทึก seed และรายการรหัสในแต่ละ split

ใช้ chat template จริง และ assistant-only loss ด้วยวิธีที่รุ่นติดตั้งรองรับ

ตรวจ token lengths ก่อนกำหนด context ห้ามตัดคำตอบจนเงื่อนไขหรือข้อยกเว้นหายโดยไม่รายงาน

ทำ pilot วัด:
- เวลาโหลดและแปลงโมเดล
- เวลาต่อ step
- throughput
- peak memory และ memory pressure
- train/validation loss

เริ่มอย่างระมัดระวัง เช่น:
- 4-bit
- batch size 1
- rank 8
- context 512 หรือ 1024 ตามข้อมูลและหน่วยความจำ
- ฝึกบางเลเยอร์ก่อน

ค่าข้างต้นเป็นจุดเริ่ม ไม่ใช่ค่าที่ดีที่สุดล่วงหน้า

ใช้ accumulation หรือ checkpointing เฉพาะเมื่อรุ่นรองรับและช่วยจริง

จำกัดการลอง configuration เลือก checkpoint จาก validation ไม่ใช้ test เลือกโมเดล

บันทึก adapter, configuration และ log เป็นระยะ ตรวจการ resume จริง และไม่อ้างว่าคืน optimizer/RNG ครบหากคืนได้เฉพาะ weights

หากหน่วยความจำไม่พอ ให้ลด workload ตามผลวัดและอธิบาย trade-off ไม่ปล่อยให้เครื่อง swap หนักต่อเนื่องเพื่อฝืนทำงาน

# 17. การประเมิน

## 17.1 โมเดลฐานกับ adapter

ใช้ prompt, quantization, context, generation settings และชุดทดสอบเดียวกัน

ประเมิน:
- held-out loss
- ความตรงกับคำตอบและหลักฐาน
- การเพิ่มข้อมูลไม่มีแหล่งรองรับ
- ตัวเลข หน่วย เงื่อนไข และข้อยกเว้น
- latency และ memory

แยกผล:
- โมเดลฐาน
- โมเดลพร้อม adapter
- ผลเมื่อเพิ่ม RAG

ใช้ตัวอย่างที่มี provenance แสดงคำตอบจริงและข้อผิดพลาดจริง

ไม่ใช้คะแนน LLM judge เพียงอย่างเดียวรับรองความถูกต้องด้านสุขภาพ

หากข้อมูลฝึกเป็นอังกฤษ ไม่อ้างว่าภาษาไทยดีขึ้นโดยไม่มีชุดทดสอบไทยที่มีคำตอบอ้างอิงจากมนุษย์หรือแหล่งต้นฉบับเหมาะสม

หาก adapter แย่กว่าโมเดลฐาน ให้เลือกโมเดลฐานสำหรับ demo และส่งมอบ adapter พร้อมผลตามจริง

## 17.2 การบันทึก

ตรวจ:
- ค่าที่แยกได้มีข้อความรองรับ
- หน่วยและเวลา
- ข้อมูลข้ามวัน
- missing และความกำกวม
- การถามเพิ่ม
- ไม่บันทึกก่อนยืนยัน
- การแก้ไขไม่ทำลายประวัติ

หากไม่มีข้อมูล annotated จริง ให้แยก software test ออกจากผลวัดความแม่นยำกับผู้ใช้จริง

## 17.3 อาหาร

ตรวจ:
- portion และฐานปริมาณ
- การแปลงหน่วย
- raw/cooked
- ผลรวมและ missing
- ไม่บวกสารอาหารซ้ำ
- provenance
- unknown ingredient/allergen

## 17.4 กิจกรรมและการนอน

ตรวจ:
- ระยะเวลา
- กิจกรรมซ้ำ
- ข้ามเที่ยงคืนและการงีบ
- เวลาบนเตียงไม่ถูกเรียกเป็นเวลาหลับจริง
- ไม่รวมค่าจากวิธีวัดต่างกันอย่างเงียบ ๆ
- ไม่สร้างความหนักหรือแคลอรีขึ้นเอง

## 17.5 Scheduler และกฎ

ตรวจ:
- ไม่มีเวลาชน
- hard constraints ไม่ถูกละเมิด
- เปลี่ยนเวลางานแล้วตรวจทุกด้านใหม่
- ข้อมูลไม่พอคืน unknown
- infeasible ไม่ถูกแสดงว่าจัดแผนสำเร็จ
- แผนที่ผู้ใช้ยืนยันยังถูกตรวจเมื่อมีข้อมูลใหม่
- ข้อความอธิบายตรงกับแผนที่ผ่านโปรแกรมตรวจ

ใช้กรณีขอบที่มีความหมาย ไม่สร้าง tests จำนวนมากที่เพียงสะท้อน implementation

รายงานความถูกต้องของโปรแกรมแยกจากความเหมาะสมทางสุขภาพ ไม่มีผู้เชี่ยวชาญตรวจจริงต้องไม่อ้างว่าผ่านแพทย์ นักกำหนดอาหาร หรือผู้เชี่ยวชาญด้านการออกกำลังกายแล้ว

# 18. Supabase และโครงสร้างข้อมูล

ฉันเลือก Supabase เป็น backend/database หลักในอนาคต

รอบนี้ทำ local demo พร้อม migrations และ interface เชื่อมต่อ ไม่ต้องตั้ง production เต็มรูปแบบหรือขอ credentials ตั้งแต่เริ่ม

โมเดลรันบน Mac ระหว่างพัฒนา ไม่วางโมเดล 4B ไว้ใน Supabase Edge Functions

เตรียมตารางหรือโครงสร้างเทียบเท่า:
- user_profiles
- user_consents
- user_constraints
- clinician_targets
- health_measurements
- medication_schedules
- medication_logs
- appointments
- foods / food_nutrients / portions
- recipes / recipe_ingredients
- meal_logs / meal_log_items
- activity_catalog
- activity_logs
- sleep_logs
- wellbeing_logs
- plans / plan_items
- plan_feedback
- source_documents / source_chunks
- rules / rule_evaluations
- audit_events

ใช้ foreign keys และ versioning ตามความจำเป็น ไม่ซ้ำข้อมูลที่ derive ได้โดยไม่มีเหตุผล

เตรียม:
- RLS แยกเจ้าของข้อมูล
- secret ผ่าน environment
- .env.example ที่ไม่มีค่าจริง
- indexes ตาม query ที่ใช้งาน
- pagination
- transaction สำหรับยืนยันแผน
- ป้องกันบันทึกซ้ำเมื่อ retry
- audit โดยไม่บันทึกข้อมูลสุขภาพหรือ secrets เกินจำเป็น
- export/delete interface สำหรับข้อมูลผู้ใช้

แยกสถานะ:
- AI เสนอ
- ผ่านโปรแกรมตรวจ
- ผู้ใช้ยืนยัน
- ผู้ดูแลตรวจจริง

อย่าใช้ boolean approved ตัวเดียวแทนทุกสถานะ

ข้อมูลผู้ใช้จริงไม่เข้าชุดฝึกอัตโนมัติ

ไม่เขียนไป Supabase จริง ไม่ deploy และไม่ติดต่อบุคคลภายนอก หากยังไม่มีการอนุญาตสำหรับขั้นตอนนั้น

อย่าอ้างว่าระบบรองรับผู้ใช้จำนวนมากโดยไม่มี load test

7. ข้อเสนอปรับแผน พร้อมก่อน–หลัง
8. สรุปข้อมูลจริงและรายการที่ยังไม่พร้อม

แสดงสถานะข้อมูลและความพร้อมรายด้านอย่างชัดเจน ไม่ให้โมดูลที่ยังไม่มีข้อมูลแสดงผลเหมือนพร้อมใช้

สาธิตจากข้อมูลที่มีสิทธิและความเหมาะสม หากยังไม่มีข้อมูลผู้ใช้ที่อนุญาต ให้ใช้ฟอร์มว่างสำหรับกรอกและแสดงข้อมูลสาธารณะตามสิทธิ ไม่สร้างผู้ป่วยปลอมให้ดูเหมือนจริง

Software fixtures แยกจาก demo ผู้ใช้และชุดฝึก

UI ใช้ภาษาไทยที่เข้าใจง่าย ไม่แสดงศัพท์ภายในโดยไม่จำเป็น และไม่ซ่อนข้อมูลที่ผู้ใช้ต้องรู้เพื่อเลือกหรือยืนยัน

# 20. โครงสร้างและไฟล์ส่งมอบ

จัดโครงสร้างโปรเจกต์ให้มีส่วนข้อมูล โมเดล services กฎ demo tests และ reports แยกกัน

ส่งมอบอย่างน้อย:

1. README ภาษาไทย
   - วิธีติดตั้ง
   - เตรียมข้อมูล
   - ฝึก
   - ประเมิน
   - รัน demo
   - ข้อจำกัด

2. dependencies ที่ทดสอบแล้ว พร้อมรุ่นจริง

3. local_training.ipynb
   - สำหรับ Jupyter บน Mac
   - เรียก scripts ได้
   - ไม่มี secrets หรือผลรันที่แต่งขึ้น
   - งานฝึกยาวไม่ต้องผูกกับหน้า notebook

4. scripts
   - ตรวจ environment
   - ดาวน์โหลดและตรวจแหล่งที่อนุญาต
   - audit/prepare/split
   - train/evaluate/inference
   - รัน demo

5. dataset manifest และ data audit
   - แหล่งที่ใช้จริง
   - จำนวนจริง
   - license
   - provenance
   - รายการตัดออก

6. train/validation/test หรือคำสั่งสร้างใหม่ ตามสิทธิการแจกจ่าย

7. adapter และ training configuration ที่ฝึกจริง หากสำเร็จ

8. training logs และผลเทียบโมเดลฐาน

9. ตัวนำเข้าฐานอาหาร activity catalog และข้อมูลสุขภาพที่เกี่ยวข้อง

10. ตัวคำนวณและ scheduler พร้อมผลทดสอบ

11. RAG พร้อม metadata และ citation

12. rule registry พร้อมสถานะการทบทวน

13. schema, migrations และ payload สำหรับ Supabase

14. local demo และ interface สำหรับเชื่อมแอป

15. รายงานความพร้อมรายฟังก์ชัน
   - ทำได้จริง
   - ทดสอบแล้วอย่างไร
   - ขาดข้อมูลอะไร
   - ต้องให้ใครตรวจ
   - ยังไม่ควรเปิดใช้ส่วนใด

เปิด process ใหม่แล้วตรวจว่าโหลดโมเดลฐานและ adapter กลับมา inference ได้จริง

หากฝึกไม่สำเร็จ ต้องรายงานสาเหตุ log และงานที่ทำได้ ไม่สร้างไฟล์ placeholder แล้วเรียกว่าโมเดลที่ฝึกแล้ว

# 21. วิธีดำเนินงานและลำดับความสำคัญ

เริ่มจาก:
1. ตรวจเครื่อง repository และคำสั่งโครงการที่เกี่ยวข้อง
2. ตรวจไฟล์วิจัยเดิมและแหล่งข้อมูล
3. ทำ source/task matrix และกำหนดขอบเขตจริง
4. ทดสอบโหลดโมเดลและทำ pilot ให้เร็ว
5. สร้าง pipeline ข้อมูลและชุดประเมิน
6. สร้าง recording, calculator, scheduler และ rule checks
7. ฝึก configuration ที่เหมาะกับผล pilot
8. เชื่อม RAG และ demo
9. ประเมิน โหลดกลับ และสรุปผล

วางแผนให้การฝึกไม่กินเวลาหรือหน่วยความจำจนพัฒนาระบบส่วนอื่นไม่ได้

ให้ความสำคัญตามลำดับ:
- ความจริงของข้อมูลและสิทธิ
- การทำงานครบกระบวนการในทุกด้าน
- การตรวจข้อมูลและข้อจำกัด
- การฝึกจริงและประเมินอย่างซื่อสัตย์
- ประสบการณ์ใช้งานที่เข้าใจง่าย
- การปรับประสิทธิภาพและความสวยงามเพิ่มเติม

เมื่อแหล่งใดติดสิทธิหรือการเข้าถึง ให้แยกโมดูลนั้นเป็น pending และทำส่วนอื่นต่อ อย่าหยุดทั้งโครงการ และอย่าเติมข้อมูลปลอม

ทำ routine choices ภายในขอบเขตนี้ได้เอง ถามฉันเฉพาะเรื่องที่จำเป็นต่อการเดินหน้าหรือเป็นการเปลี่ยนขอบเขตสำคัญ

ส่งความคืบหน้าเป็นระยะโดยเน้นสิ่งที่พบ ปัญหาที่มีผลต่อผลลัพธ์ และสิ่งที่จะตรวจต่อ

ผลลัพธ์สุดท้ายต้องบอกได้ตรงไปตรงมาว่า:
- เราฝึกอะไรด้วยข้อมูลของใคร
- โมเดลดีขึ้นหรือแย่ลงตรงไหน
- แต่ละโมดูลอาศัยข้อมูลและหลักฐานอะไร
- แผนถูกตรวจด้วยอะไร
- อะไรยังต้องใช้ข้อมูลหรือผู้เชี่ยวชาญเพิ่มเติม

เริ่มลงมือสร้างต้นแบบตามข้อกำหนดนี้ โดยตั้งเป้าให้ได้ระบบดูแลกิจวัตรหลายด้านที่ตรวจสอบได้ภายในงบเวลา ไม่ใช่เพียงแชตบอตตอบเรื่องอาหาร
